# Smart Money feasibility

## Smart Money 3.0 Debug configurations

The default Debug and Release configurations exclude the automatic SMS receiver and its restricted permission. The separate local experiment uses `-PlifeosPrivateSms=true` with `:app:assembleDebug` and adds only `android.permission.RECEIVE_SMS`. Both Debug configurations use `com.lifeos.personal.debug` and the existing Debug signer. Paste and Android Share work in both configurations.

The private receiver starts disabled. The user enables it in Profile → Money & Imports after the permission explanation. The UI checks Android’s grant and the receiver’s enabled state. When Android will no longer show a prompt, the settings page links to the app’s Permissions screen. Permanent denial and an installer restriction can appear alike to the app. Android documents this permission as hard restricted and dependent on installer allowlisting. The receiver uses the system SMS broadcast and assembles the parts of a delivered message. [Android permission reference](https://developer.android.com/reference/android/Manifest.permission#RECEIVE_SMS) · [Android SMS broadcast](https://developer.android.com/reference/android/provider/Telephony.Sms.Intents#SMS_RECEIVED_ACTION)

The receiver does a coarse local financial check and writes eligible text to a bounded, AES-GCM encrypted staging file with atomic replacement. The separate staging key is device-bound and can be used in the background after Android has unlocked the device. The main ledger key remains behind LifeOS authentication. Staging uses an authenticated binding derived inside the vault and a no-backup directory. JavaScript can inspect alert text only during foreground, protected, authenticated review. The same offline parser handles SMS, paste and Share. The encrypted ledger receives reviewed fields, source, reference and duplicate identity after confirmation. [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

The queue holds up to 32 outstanding alerts and drops expired entries on its next access after 72 hours. Confirming or dismissing removes the text and leaves a bounded encrypted receipt digest until expiry. Disabling monitoring closes the receiver before returning and leaves confirmed transactions intact. Clear pending suggestions erases the staging file. Data reset or backup replacement turns the receiver off and clears the queue. Staging stays outside LifeOS backups.

Native delivery and permission behavior require a real isolated Android run. Browser mocks exercise the review UX and the encrypted ledger. An authorized Android emulator can simulate incoming SMS with synthetic banking text through its console. [Android emulator SMS simulation](https://developer.android.com/studio/run/emulator-console#sms)

## Paste and Android Share

Money → Transactions has **Import alert**. Android also lists LifeOS Debug for individual plain-text shares from compatible apps. The cold and foreground paths hand the alert to the same review screen after session validation. A new workspace can opt into protected storage from **Review shared alert**. Detection runs on-device and clears the text input. The user can edit the suggestion and explicitly confirm it in the transaction composer. The encrypted record contains the confirmed fields and a duplicate-check digest.

Android queues up to three distinct alert texts in process memory for five minutes, with a 2,000-character limit per alert. Process loss clears the queue. A lock removes raw text from the UI. Unlocking within the queue window can reopen the original alert, with any unsaved text edits discarded. After the user opens the transaction composer, the app acknowledges and clears the original. An Android share intent supplies unverified text. The receiver strips the payload from the Activity intent before Capacitor dispatches it, and every ledger write still requires user confirmation.

The parser recognizes common English bank debit and credit messages, UPI alerts, card purchases, and ATM withdrawals. It supports explicit currency codes, selected unambiguous currency symbols, Indian digit grouping, and explicit Indian or ISO dates. It separates the transaction amount from a trailing balance or available limit. Messages with conflicting directions or multiple transaction amounts need manual review. A bare dollar sign leaves the currency unknown. The account suffix is a hint, and the user chooses an account. Missing dates require input and missing times remain unset.

Failed and pending alerts, OTPs and obvious promotions cannot enter the transaction composer. Refunds and reversals are recognized for review without posting them as income or expenses. A user can send a suspected transfer to the existing Accounts transfer composer. It still requires both accounts and an explicit save. It never uses an income or expense row.

The encrypted write coordinator rejects an exact reference or text fingerprint inside the same atomic transaction that adds the record. It checks compatible vc1000009 fingerprints as well. A candidate with the same amount, date, currency and direction also needs a matching description or a matching account and timestamp to trigger the possible-duplicate confirmation. Only that uncertain match can be overridden. A different description or a missing bank reference can leave too little evidence to distinguish an import from an existing manual entry. Historical financial records keep their existing representation.

## Android and Google Play

Google Play lists SMS-based money management as a reviewed exception for `READ_SMS`, `RECEIVE_SMS`, `RECEIVE_MMS`, and `RECEIVE_WAP_PUSH`. Eligible apps declare their use in Play Console and document how the permission serves critical core functionality advertised in the store listing and why a less sensitive method is insufficient. LifeOS has a weak eligibility case in its current form. Tasks, Habits, Goals and manually managed Money work independently of message access, and user-directed paste and Android Share already handle individual alerts. An unapproved declaration risks rejection or removal on Play. Android also hard-restricts SMS access, so an installer allowlist and the relevant runtime permission apply even when distributing outside Play. [Play SMS and Call Log policy](https://support.google.com/googleplay/android-developer/answer/10208820) · [Android manifest permission reference](https://developer.android.com/reference/android/Manifest.permission#READ_SMS)

An eventual Play-approved provider would need separate opt-in at the point of use, prominent in-app disclosure of the SMS scope and purpose, a current privacy policy, minimal message access and retention, and a way to revoke the permission. `TransactionAlertProvider` lets sources reuse the parser and confirmation boundary. The default build uses Android's plain-text sharing contract and requests no SMS permission. SMS Retriever is for app-specific verification. Notification Listener and Accessibility remain outside the provider design. [Play User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311) · [Android sharing](https://developer.android.com/develop/ui/compose/sharing/receive) · [SMS Retriever purpose](https://developers.google.com/identity/sms-retriever/overview)

## CSV and cross-platform compatibility

CSV import remains a separate provider option behind the same review step. A user-selected file can use the system document picker for scoped URI access. Bank-specific column maps, signs, locale-specific formats, reference matching and overlapping statement ranges would need validation. [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files)

On iOS, a future explicit import can use the document picker and, if appropriate for the host and extension policies, a user-directed share extension. IdentityLookup is a filtering API scoped to certain SMS/MMS from unknown senders and does not provide a general transaction inbox feed. Paste-based parsing itself does not depend on OS inbox APIs. There is no native iOS verification for this candidate. [Apple document picker](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller) · [Apple Share extensions](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html) · [Apple SMS and MMS filtering](https://developer.apple.com/documentation/identitylookup/sms-and-mms-message-filtering)

## Optional bank integrations

In India, assess a regulated Account Aggregator partnership and whether a qualifying regulated Financial Information User can provide the intended service. A production integration needs eligible parties, an explicit purpose-bound consent artefact, authenticated interfaces, revocation and the appropriate operational agreements. In the UK, bank account information access involves authorised or registered providers and explicit customer consent. Eligibility and rules vary by region. The implementation decision depends on target markets, authorised partners, consent flows, privacy and retention design, and a review of provider contracts and applicable regulation. [RBI Account Aggregator Directions](https://www.rbi.org.in/Scripts/NotificationUser.aspx?Id=12936) · [FCA information for third-party providers](https://www.fca.org.uk/firms/account-information-services-payment-initiation-services)
