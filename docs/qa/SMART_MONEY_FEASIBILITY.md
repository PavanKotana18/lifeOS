# Smart Money feasibility

## Available in this Debug candidate

Transactions has Import alert. The user pastes a single alert, asks LifeOS to detect a transaction, and reviews the suggestion in the usual transaction composer. Detection runs on the device. The pasted text is cleared from the input after detection. The composer uses the existing encrypted write path and requires explicit confirmation. It stores the reviewed fields and a duplicate-check fingerprint in the encrypted transaction. It does not copy the raw alert, bank hint or reference to the ledger.

The parser recognizes a limited set of English bank-alert patterns, explicit ISO currency codes and unambiguous currency symbols. It accepts Indian digit grouping and explicit day-first dates for INR alerts. It accepts ISO dates and an explicitly supplied local time. Bare dollar signs, unsupported separators and ambiguous amounts require manual entry. Merchant, date, time, masked account suffix and reference are extracted only when the pattern supports them. The account suffix is a hint and never selects an account automatically. Missing dates require input, and unknown times remain unset.

Failed and pending alerts, OTPs and obvious promotions cannot enter the transaction composer. Refunds and reversals are recognized for review without posting them as income or expenses. A user can send a suspected transfer to the existing Accounts transfer composer. It still requires both accounts and an explicit save. It never uses an income or expense row.

The encrypted write coordinator checks stable reference-derived identity when sufficient reference fields are available and a normalized text fingerprint otherwise. It also rejects an exact date, account, amount, currency, direction and description match, with time used where both records have it. This conservative check can reject similar legitimate transactions. It covers confirmed imports and checks their identity inside the write transaction. Different descriptions, omitted references and cross-feed imports can evade any heuristic that lacks a stable bank-provided ID.

## Android and Google Play

Android declares SMS reading and receiving hard restricted. A runtime prompt alone is insufficient. Google Play lists SMS-based money management as a possible exception subject to review. The app must declare eligible permissions through Play Console, show that the use case is core, and document why a less sensitive method is insufficient. Any applicable disclosure and consent requirements also apply. No policy approval or automatic feed is part of this build. The permission inventory and onboarding remain as in vc1000008. [Android manifest permission reference](https://developer.android.com/reference/android/Manifest.permission#READ_SMS) · [Google Play SMS and Call Log policy](https://support.google.com/googleplay/android-developer/answer/10208820)

An Android share target could accept text the user explicitly shares via ACTION_SEND. It needs validation of caller-delivered MIME type and bounded text, secure handoff while the app is locked, and no background inbox access. A bank CSV file can be chosen through the system document picker for scoped URI access. Neither path needs broad SMS access. SMS Retriever is intended for app-specific verification messages and is not a bank-alert ingestion path. Notification Listener and Accessibility services are outside the design. [Android sharing](https://developer.android.com/develop/ui/compose/sharing/receive) · [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files) · [SMS Retriever purpose](https://developers.google.com/identity/sms-retriever/overview)

## CSV and cross-platform compatibility

CSV import should be a separate provider behind the same review step. Before enabling it, test bank-specific column maps, delimiters, quoted data, locale-specific dates and decimals, separate debit and credit columns, credit-card sign conventions, transaction versus posting dates, and ISO currency. Leave unknown fields open for review. Use stable statement IDs or scoped reference/digest matching, and detect overlap between overlapping statement ranges. Limit file and row sizes and keep the raw document out of the ledger. User-selected files and native share receivers are feasibility findings in this candidate.

On iOS, a future explicit import can use the document picker and, if appropriate for the host and extension policies, a user-directed share extension. IdentityLookup is a filtering API scoped to certain SMS/MMS from unknown senders and does not provide a general transaction inbox feed. Paste-based parsing itself does not depend on OS inbox APIs. There is no native iOS verification for this candidate. [Apple document picker](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller) · [Apple Share extensions](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html) · [Apple SMS and MMS filtering](https://developer.apple.com/documentation/identitylookup/sms-and-mms-message-filtering)

## Optional bank integrations

In India, assess a regulated Account Aggregator partnership and whether a qualifying regulated Financial Information User can provide the intended service. A production integration needs eligible parties, an explicit purpose-bound consent artefact, authenticated interfaces, revocation and the appropriate operational agreements. In the UK, bank account information access involves authorised or registered providers and explicit customer consent. Eligibility and rules vary by region. The implementation decision depends on target markets, authorised partners, consent flows, privacy and retention design, and a review of provider contracts and applicable regulation.
