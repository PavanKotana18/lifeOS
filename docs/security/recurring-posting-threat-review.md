# Recurring occurrence posting: threat and integrity review

Review date: 2026-11-17. Scope is the confirmation-first Money milestone for planned income and expense occurrences. This review inspects the production code and focused regressions; it is not native authentication, Android delivery, store, or bank-payment acceptance.

## Assets and trust boundaries

Protected assets are exact transaction amounts/currency, private descriptions and account/category links, the occurrence's immutable identity, plan cadence/history, and the user's explicit confirmation. The UI is not the authority for posting eligibility: it passes the reviewed plan snapshot to the protected `StorageService.commitments.postOccurrence` boundary, which validates the current stored plan and references again. Existing session admission, native key protection, encrypted record codec, repository write lease, and atomic Dexie commit remain the persistence authority.

Application code in the same origin is trusted. Web Locks coordinate cooperative writers that share that origin/storage partition; they are not an authorization system or protection from hostile same-origin scripts, a compromised runtime, arbitrary direct IndexedDB mutation, or a user intentionally restoring an older valid backup. Those threats remain governed by the broader application threat model. No new network service, plaintext occurrence database, automatic payment, or background posting authority is introduced.

## Threats and controls

| Threat or failure | Implemented control | Review and regression evidence |
|---|---|---|
| Double tap, repeated confirmation, restart, or same-occurrence posting from another context | A transaction's occurrence ID is SHA-256 of the plan ID and scheduled calendar date; insertion uses `add`, not overwrite. Stored plan/date markers allow an already posted retry to return the original transaction. | `postOccurrence` in `encryptedStorageFacade.ts`; `test_commitment_occurrences.cjs` covers concurrent calls, durable retry, backup round-trip, runtime restart and independent storage contexts. |
| Post races an edit, reference change, deletion, clear or restore | Both local `coordinator` and `occurrenceCoordinator` acquire `lifeos-encrypted-storage-writes` before invoking the underlying coordinator. The lock covers reads, encryption preparation and commit. Every facade `coordinator.run` uses that wrapper, including reference changes and backup operations. | The previous realm-local queue was insufficient across tabs. `test_commitment_write_lock.cjs` loads the helper in separate VM contexts and verifies ordering/release; occurrence integration tests use separately loaded production runtimes and exercise edit, delete and reset races. |
| Lock API absent or lock acquisition rejected | Posting requires cross-context locking and rejects before invoking its storage operation if Web Locks are unavailable. Legacy planning and other existing facade operations retain their prior fallback. Any lock-request rejection propagates; it never falls back to an unlocked retry. | `commitmentWriteLock.ts`; focused unsupported-posting, fallback, rejected-request and failure-release tests. A supported engine means a secure context with a working lock API, not merely a particular user-agent string. |
| Deadlock from wrapping a coordinator twice | Each facade operation chooses exactly one local wrapper over `underlyingCoordinator.run`. Posting uses `occurrenceCoordinator`; other mutations use `coordinator`. The commitment callbacks no longer acquire another explicit Web Lock. The low-level transaction coordinator remains unchanged. | Static review found no nested lock acquisition or facade callback that recursively calls either coordinator. Shared-lock callbacks operate through `ctx` methods, never repository write methods. |
| Cancelled confirmation or stale reviewed amount/type/account/date | Cancellation does not call the write callback. Posting compares the reviewed snapshot with current amount, currency, type, title/notes, category/account, due date/frequency/status, update time, cadence anchor and history; changed snapshots reject. Active, due, valid-reference checks happen in storage. | Actual component handler tests in `test_commitment_occurrence_ui.cjs`; stale plan, invalid/missing category, inactive account, paused/future plan and invalid ID tests. A previously posted retry is read-only and may return the original transaction. |
| Partial post after encryption or database failure | Occurrence `ctx.add('transactions', ...)` and plan `ctx.put('plannedCommitments', ...)` prepare ciphertext first, then share the existing single multi-table Dexie transaction. Any commit failure rolls back both. | The occurrence fixture injects a failure into the real encrypted plan-update hook, compares all ciphertext tables before/after, and proves the failed post remains safely retryable. |
| Creation or mutation of occurrence provenance through ordinary transaction APIs | Normal transaction add rejects nonempty occurrence markers; transaction update preserves stored `commitmentId` and `commitmentOccurrenceDate`, regardless of proposed changes. Plan updates preserve `lastPostedDate` and reset the cadence anchor only on an explicit schedule change. | Static inspection of transaction/plan facade methods and existing validation. Public UI forms do not expose occurrence identity or history controls. The deterministic ID is a data-integrity aid, not a secret. |
| Delete a posted transaction then accidentally replay the same occurrence | `lastPostedDate` survives transaction deletion. Posting rejects an old reviewed occurrence even if its original transaction is gone; next due dates must follow recorded history. | Occurrence deletion/replay regression. Editing an already posted transaction may change its financial fields but not its original scheduled provenance. |
| Malformed backup invents conflicting occurrence identity or erases replay protection | Import validates paired plan/date markers, valid dates, unique occurrence tuples across transaction IDs, plan type/category compatibility, recurrence anchor when history exists, and surviving-plan history at least as recent as linked transactions. Invalid replacement imports fail before mutating any table. | `db.ts` validation and malformed backup cases in `test_commitment_occurrences.cjs`, including pair omission, duplicate tuple, missing/old history, rewound next date, mismatched category and missing anchor. |
| Currency drift or inaccurate financial totals | Posted amount/minor units/currency are copied from validated plan facts. Categories match income/expense type; accounts are optional but must exist, be active and use the same currency. Planned rows remain outside analytics until a transaction is posted. | Existing financial validators and exact-money services are reused. Domain recurrence advances calendar components without local-to-UTC conversion or inferred transaction time. |
| Session expires or lock occurs while waiting | The storage proxy and existing protected session/write-lease behavior remain active; Web Locks do not unlock a session or create keys. A locked session cannot retrieve a prior idempotent transaction through the posting API. | Locked-session occurrence fixture and existing security/session regressions remain required. No native authentication bypass or new crypto primitive was added. |
| UI implies automatic money movement | The confirmation names exact amount/currency, type, date, category and account, explains that the next due date advances, and states that this is not bank-payment confirmation. UI help explicitly says there is no automatic posting or bank payment. | SSR/actual-handler regression verifies due/paused/future states, reviewed snapshot and cancel behavior; actual browser keyboard and screen-reader acceptance remain separate evidence. |

## Import, deletion and history policy

A surviving plan must retain history consistent with its linked occurrence transactions, and a deleted transaction does not rewind that plan. A plan itself may be deleted while its posted transactions remain; their original `commitmentId` is provenance, not a required live-plan foreign key. Creating a new plan uses a new generated ID rather than reusing a deleted plan's identity. An explicitly approved restore of an older valid backup intentionally restores an older ledger and eligibility snapshot; this local app cannot promise permanent exactly-once history across user-directed rollback to a backup that predates an occurrence. There is no external bank side effect in this milestone. Automatic posting, restore reconciliation with external events, immutable audit trails and advanced reversal/skip policies need separate design before expanding this guarantee.

## Acceptance and remaining limits

The focused acceptance set is `test_commitment_recurrence.cjs`, `test_commitment_occurrences.cjs`, `test_commitment_occurrence_ui.cjs`, and `test_commitment_write_lock.cjs`, followed by the complete JavaScript, Sentinel, TypeScript and Vite checks and protected GitHub CI at the exact head. The delivery coordinator records executed results and merge SHA; this document does not relabel pending full checks or skips as passes. The source review finds no remaining blocker in the reviewed lock/atomicity/idempotency/backup design, subject to those tests and CI passing.

Cross-context guarantees apply to participating facades using the shared lock; direct internal repository calls are not a public feature API. The low-level migration path retains its existing compare-and-replace safeguards. Web Lock acquisition can wait for another legitimate operation; failures must remain visible and must not trigger unlocked work. Unsupported engines can still manage plans through existing CRUD, but safe occurrence posting remains unavailable. Current financial storage's numeric compatibility limits remain enforced even though authoritative values are exact minor units. Natural Android reminder delivery, biometric/device-credential consent, process-death behavior, and iOS execution are not established by these synthetic fixtures. No physical phone, production user database, secret material, or local emulator execution was used for this review.
